品连云仓WMS系统

智能仓储管理系统，支持密集存储、异地调拨、共享库存、动态盘点、缺货预警等功能

复杂业务逻辑 / 用户体验 2019

让每次扫描，都有清楚的下一步

仓储界面的价值，在于让现场人员持续知道：现在处理哪件货、应该放到哪里、数量是否一致，以及什么时候必须停下来。品连云仓的设计难点，是把复杂单据关系转化为可执行、可核对的作业顺序。

品连云仓 WMS 面向跨境电商仓储场景。原项目介绍涉及密集存储、异地调拨、共享库存、动态盘点和缺货预警；本次保留的界面重点覆盖到货、退货质检、拣货、复核、集包与客户资料。以下从这些实际界面复盘任务组织与交互取舍，并单独指出需要继续验证的环节。

  • 项目背景2019 年仓储管理项目，关注复杂业务中的桌面端作业体验。
  • 设计视角减少现场操作对记忆的依赖，让单据、实物和处理记录保持可对照。
  • 证据边界截图中的数量、日期与状态是设计样例；没有现场测试记录支持效率提升或成本下降的量化结论。

同一套系统，承接不同节奏的工作

从页面任务可以归纳出三类使用情境：主管寻找积压与异常，现场人员连续扫描，资料维护人员处理客户与货主关系。这是基于界面的任务分析，不是通过访谈建立的用户画像。三类工作分别需要总览、明确反馈和完整上下文，不能仅靠一张通用表格解决。

任务情境判断阻力原稿中的设计回应继续验证的问题
主管查看任务入口多，待办容易淹没在统计中常用功能、任务徽标、作业统计并列高频任务能否在首屏直接开始
现场扫描作业视线在货物、条码和屏幕之间切换当前商品、播种位、数量和记录分区错扫与重复扫描时是否能立即察觉
客户资料维护客户、审核与货主信息有关联但责任不同基本资料、审核资料、货主列表分区修改范围与审核结果能否清楚区分

工作台：从知道发生了什么，到开始处理

工作台同时承担统计汇总与任务导航。原稿把全局业务放在顶部，把常用功能放在侧边和快捷区，让熟悉岗位的人可以直接进入任务。值得继续推敲的是，宣传横幅占据了较多首屏空间，而部分作业入口需要向下寻找。

入库交接：先建立对应关系，再确认数量

到货通知列表、通知详情与创建卡板三张界面，共同回答“这一批货从哪里来、归属谁、当前接收到了多少”。下面是根据页面重建的任务路径；质检、上架虽有菜单入口，但本组截图没有展示它们的完整执行链。

  1. 定位通知用来源单号、来源类型、仓库与状态找到本次到货。
  2. 核对差异打开详情，对照计划数、收货数与商品明细。
  3. 建立卡板创建或输入卡板号，扫描运单并记录包裹重量。
  4. 交接后续保留来源关系，进入相应质检与上架任务；具体流转规则待补充。

从一张到货单，追到每一个包裹

列表应支持快速定位与横向比较；详情应解释差异；扫描界面应承接实际动作。将三种信息密度分开，才能让工作人员在需要时取得更多信息，而不是始终面对所有字段。

退货质检：让本次输入与累计结果分开

销退场景多了“收到以后能否继续使用”的判断。原稿按客户和运单分组，再把商品的计划、QC 完成、封箱与本次良品/次品分开。重点是让本次操作在历史进度中有明确位置。

  • 保留业务归属处理多客户退货时，客户与运单分组应一直可识别，避免把相似 SKU 记入另一批货。
  • 把约束放在输入处良品、次品、待处理数量的关系应在提交前解释清楚；原稿未提供完整校验规则。

拣货批次：先看到工作量，再作出分组决定

拣货单生成页没有直接把全部订单交给操作者。它先提供仓库、订单类型、包裹类型、渠道与发货剩余时间等条件，再汇总筛选结果。设计意图可以理解为：在生成任务前，让操作者先判断这批工作是否适合当前处理能力。

  1. 限定范围确定仓库、包裹类型与时效条件。
  2. 组合渠道在运输方式树中选择本批次的物流范围。
  3. 预览工作量检查包裹、订单、SKU 与商品数量。
  4. 生成拣货单确认分拣上限与选择范围后建立任务。

多品播种：把商品与物理格位对上

多品播种要把一批拣回的商品分配到对应容器。原稿把“当前正在扫的商品”“应该放入的格位”“整批完成情况”分成三个区域。格位图负责空间定位，列表负责记录追溯，两者服务于不同的判断。

  • 空间映射保持格位编号与现场容器一致，让画面中的位置能直接对应手边动作。
  • 冗余反馈颜色之外保留编号、数量和完成符号；需要验证远距离识别与色觉差异下是否仍能区分。
  • 异常恢复错放与重复扫描不能仅改变颜色，应说明受影响的商品、格位和恢复方式。此为后续方案。

单品复核：让完成和异常成为两条清楚的出口

单品复核页进一步收窄任务：先识别容器或拣货单，再扫描商品。右侧大状态区让人员在短暂抬头时确认工作状态，F1 完成与 F2 异常上报则将两个结果出口并列放置。

  1. 建立上下文扫描容器编号或拣货单号，明确正在复核的任务。
  2. 核对商品扫描条码，查看商品图、规格与数量。
  3. 判断一致性对照订购数、已检数、差异与取消标记。
  4. 选择出口一致后完成；存在差异时进入异常上报，不强行结束。

集包称重：分清当前袋与已完成记录

完成单件或订单层面的复核后，集包界面需要建立另一种粒度：哪些包裹属于当前集包、采用什么渠道、重量如何汇总。原稿的左右分区将正在处理的袋与集包列表分开，有助于持续扫码时保留当前任务。

客户档案：将资料维护与审核责任分开

仓储作业离不开客户、货主和仓库的对应关系。原稿用同一页面保留三类信息，但分别设置操作入口：基本信息用于日常维护，审核信息用于判断资料状态，货主列表用于管理关联主体。

从静态稿到可用作业：优先补齐三类反馈

这组设计体现了清楚的任务分区，但现场可靠性还取决于静态图里看不到的交互契约。以下是根据画面提出的改进方向，不能视为原系统已经具备的能力。

触发情境界面需要回答什么建议设计动作如何验证
错扫或重复扫码这次扫描是否被计入，属于哪一个任务固定区域显示条码、失败原因与未计入说明，保留当前任务连续扫入正常码、重复码与不属于本单的码，观察识别和恢复
数量不一致差异在哪一行，是否可以继续将异常行和差异说明与完成条件关联，提供返回核对入口混合正常与差异行，检查是否会误以为全部完成
称重或打印中断是数据未保存，还是设备动作未完成分开展示记录保存与打印状态，明确重试范围在扫码、保存、打印各阶段模拟中断，核对有无重复记录

复盘：用可验证的任务替代笼统的效率承诺

这组 WMS 设计最值得保留的，是把批次、商品、格位和记录分别放在合适的区域，再用稳定的位置建立操作预期。若继续迭代，我会优先验证扫描与异常恢复，再调整工作台入口优先级；视觉精简应服务于更少的判断负担。

验证任务观察项记录方式
从工作台找到一笔部分收货单首次选择入口、返回次数、差异定位是否正确用同一任务对比入口前置前后的过程，保留逐步记录
完成播种并处理一次错扫是否识别目标格位、错误发现位置、恢复步骤结合真实工位与扫码设备测试，不只在鼠标原型中计时
从复核转入集包并处理打印失败任务归属是否保持、是否重复保存或打印同时核对操作者理解与实际业务记录
补交一项未通过的客户资料是否理解失败原因、修改范围与保存结果观察从查看、编辑到提交的完整路径

以上验证尚未执行。异地调拨、盘点与缺货预警的完整页面也未包含在这组留存稿中，因此没有为它们补写未经证实的交互方案或上线成果。
