OMS订单管理系统

多电商平台订单统一管理系统

UI组件 / B端视觉 2020

让订单状态，成为行动的依据

多平台订单管理的难点，是让运营在商品、仓库、履约和售后之间切换时，仍能准确判断：这笔业务当前到了哪里，由谁处理，以及现在允许做什么。

这是我在 2020 年业余时间参加墨刀 UI 组件赛事的投稿作品，以多电商平台订单统一管理为场景，探索桌面端界面与组件规则。我关注的是商品、库存、订单和售后之间的信息衔接，以及同一套组件如何适配不同业务对象。

  • 设计对象商品资料、入库、库存、销售订单、结算、售后、评价和角色配置。
  • 设计重点让跨模块的列表、表单和状态表达保持一致，同时保留业务对象之间的差别。
  • 项目性质界面与组件概念设计，侧重任务组织、信息层级和交互规则。

从模块目录，转向运营任务

菜单按业务对象划分，实际工作却会穿过多个模块。一次缺货判断可能需要查看库存，再回到销售订单；一次退款核对则涉及订单、售后与结算。我按任务整理这些信息关系，再分别考虑操作范围与角色分工。

任务需要连续理解的信息页面设计仍待补齐
维护可售商品商品属性、物流限制、销售平台和审核状态商品列表、编辑表单、分类树属性适用范围与审核反馈
判断订单如何履约平台来源、内部订单、可售量和仓库进度库存明细、销售列表、订单时间线同步异常、库存占用与跨模块回查
处理售后与核账原订单、退款单、物流和资金明细售后列表、退款详情、结算列表退款失败原因与处理结果回写
分配日常职责可见模块与允许执行的动作菜单层级和功能权限树角色模板、数据范围与授权预览

经营概览：从趋势回到具体待办

页面把交易趋势和订单趋势分开，又提供交易明细与订单列表入口。这种“摘要—明细”的结构使概览有机会成为任务起点。关键不是图表越多越好，而是每个指标能否回答同一时间范围下的一个明确问题。

商品资料：按使用目的拆分长表单

商品既用于展示与检索，也会影响物流和销售范围。页面将基本属性、物流、图片和其他信息分区，让录入者逐组完成。这比一个无限延伸的字段列表更有结构，但组件复用仍需要检查当前商品是否适合显示这些属性。

  • 分组解决查找同类字段相邻，查看和编辑维持相同次序。
  • 条件显示减少负担按商品类别呈现相关属性，避免填写不适用信息。
  • 就地校验减少返工单位、范围、必填项和错误说明靠近输入，保存前明确还有哪些问题。

分类管理：小弹窗承接局部动作

分类属于有层级的对象，用树能同时表达名称与父子关系。增加一个下级分类时，保留底层树状上下文比跳转到全新页面更容易理解新节点会出现在哪里。

入库准备：先定仓，再选择要到达的商品

这一段任务从选择目的仓开始，再录入物流信息、添加商品与数量，最后提交审核。它描述的是运营侧的入库准备；不能将“提交审核”理解成货物已经进入可售库存。

  1. 确定目的仓先建立单据归属，避免填完商品才发现仓库选错。
  2. 填写物流区分自送与承运信息，补充预计到达时间。
  3. 选择商品在已有资料中检索规格，核对箱号与数量。
  4. 提交并追踪提交审核后回到单据，继续查看确认和在途状态。

入库单与库存：进度和数量分别表达

订单汇集：统一身份，保留平台来源

销售列表同时呈现内部订单号、平台订单号和运单号，分别服务于系统追踪、平台核对和物流查询。手工建单与文件导入保留为独立入口；对于平台同步，下一步需要明确数据来源、更新时间和异常处理方式。

一次导入完成后，使用者应该知道什么

我把导入拆成一次可回查的处理过程，重点区分“文件已收到”和“订单已创建”。下一步希望补齐校验预览、部分成功和失败重试，让用户能够定位问题，而不必重新上传整个文件。

  1. 准备模板下载当前字段模板，确认平台订单标识及格式。
  2. 预检内容列出缺失字段、重复记录与无法识别的商品。
  3. 确认写入显示将创建的订单范围，以及被排除的行。
  4. 回查结果提供成功与失败清单；修正后只重试未完成项。

状态不是一条直线：给异常保留分支

订单时间线说明正常履约，拦截、退款与异常则是独立分支。将所有状态排成一串，容易让人误以为每笔订单都要经历退款。我用以下矩阵整理不同情境下的操作，以及需要明确的限制。

当前情境可用的动作与信息需要补足的交互约束
待发货查看、拦截订单展示影响的订单与原因；确认拦截是否成功，避免与发货同时发生时误判
仓库处理中履约进度与当前阶段明确最后同步时间、当前处理方与允许操作，不能假定已完成交接
已发货查看、申请售后保留物流与原订单信息，进入独立售后过程
已拦截查看、部分行显示取消拦截解释恢复条件与恢复后的目标状态
异常或退款失败顶部有异常和失败统计提供失败原因、负责人、重试范围和结果记录

结算与售后：分开货物流转和资金结果

售后处理既关心商品，也关心退款。页面将结算与售后作为独立模块，并在退款详情中保留原订单和物流信息。分开模块有利于控制信息密度，代价是必须提供足够清楚的关联方式。

从发现退款问题，到回到交易记录

基于售后与结算两组页面，可以形成一条有明确交接点的核对路径。图中“处理与同步”属于待完善环节，真实流程仍取决于平台、仓库与财务规则。

  1. 定位售后从退款状态与原订单号找到待处理记录。
  2. 核对上下文检查退款方式、商品、发货状态与相关单号。
  3. 处理与同步明确处理方、失败原因和重试边界，反馈处理后的状态。
  4. 回查交易通过原订单关联资金明细，核对最终结果与时间。

评价与权限：复用表达，保持语义准确

相同的图表、列表和树状组件可以服务多个模块，但组件的形状相同，不代表含义相同。评价分数和订单占比需要不同口径，功能勾选也不能被误认为全部授权已经生效。

组件复用的边界，是业务语义

本项目作为组件赛事作品，值得继续推进的方向是“相同任务用相同表达，不同对象保留不同约束”。列表、表单、选择器与状态摘要可以复用布局；字段名称、主操作、统计口径和错误信息必须随着业务对象重新校验。

复用组件应保持一致必须随业务变化优先验证任务
列表与工具栏筛选、选择、批量操作和分页位置商品审核、入库确认、订单导入的动作语义从库存页找预警设置，观察是否被订单动作干扰
长表单与选择器分区、必填提示、已选反馈和保存位置类别属性、物流限制与地址规则新增非服饰商品，检查不适用字段是否造成误填
状态与时间线名称清楚、当前位置突出、可回查履约、拦截、退款分别有哪些分支解释一笔已发货但待退款的订单，观察是否混淆完成状态
统计摘要与图表时间范围、单位、口径和明细入口金额、件数、订单数、评分各自的定义从异常统计找到对应订单，核对筛选与总数是否一致

设计回顾：让一致的组件表达不同业务

这组探索建立了从商品准备到订单和售后的整体界面框架，也暴露出复制组件时最容易遗漏的部分：行为和文案是否属于当前任务。下一步不会先增加更多看板，而会优先修正商品搜索、库存工具栏与导入结果反馈，再验证跨模块状态能否被正确理解。

下一轮计划从四个任务验证：维护非服饰商品、创建入库并追踪在途状态、导入含重复行的订单文件，以及核对待退款订单。记录完成情况、误判位置与恢复路径；平台同步、库存和退款的业务规则，与开发及业务方共同确认。
