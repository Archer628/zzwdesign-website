Michaels 运维支持系统

Michaels技术团队（深圳）运维支持系统

业务逻辑 / 数据管理支持 2022

把分散的运行信息，组织成可处理的问题

Michaels 运维支持系统面向深圳技术团队内部使用。2022 年，我负责相关 UI/UX 设计，包括开发需求对接、初始框架与风格设定、高保真设计、设计系统维护及开发交付。核心页面围绕前端告警、模块与页面看板、基础配置展开。

  • 设计重点让告警容易发现、筛选和理解，让监控对象有明确归属，让配置规则可以解释。
  • 功能分工应用中心统一提供工具入口，前端告警监控内部再按任务展开列表、详情、看板与配置，避免混淆不同工具的操作范围。

工作空间先回答：我正在看哪个系统

一个后台可以共用框架，但不同应用的对象和风险并不相同。全局层负责“在哪里”，应用导航负责“做什么”，内容区再回答“正在处理哪条记录”。这样的分工能避免所有入口都挤在同一级菜单，也给后续工具接入留下清楚的位置。

告警列表，先筛选再采取行动

这里的难点是信息密度。告警 ID 和 HASH 有定位价值，却很长；等级、环境和模块更适合快速筛选。我优先让可判断的信息稳定可见，再为长标识提供完整查看与复制。固定操作列便于找到动作，批量操作则必须说明作用范围。

要作出的判断页面提供的线索需要明确的设计规则
是否优先查看告警等级及 Open / Closed 状态等级定义与排序依据分开说明，不把已关闭高等级告警当作当前待办
是否属于当前范围环境、模块和筛选条件切换详情后保留筛选上下文；生产与测试环境使用文字标识
能否执行批量动作行选择、批量操作及更多菜单明示选中数量、作用范围与不可执行项；涉及删除时说明后果

详情页，围绕一次事件重建上下文

告警详情按“事件摘要—发生条件—行为与完整报文”逐层展开，让使用者根据需要追查。标识、时间、环境和模块应持续可见，返回列表时保留原位置。日志访问、脱敏与复制范围则需要按角色权限约束，在联调中一并核对。

模块与页面，是两种观察尺度

模块用于发现一片范围的变化，页面用于收窄到具体入口。两种看板需要形成可追溯关系，我将定位层级组织为“工作空间—模块与环境—页面—事件”，让每次下钻都知道正在缩小哪一层范围。

  1. 工作空间确定当前团队和工具，建立操作范围。
  2. 模块与环境确认是哪一项业务、哪一套运行环境，避免跨环境比较。
  3. 页面通过业务名称与完整 URL 找到具体监测对象。
  4. 事件查看该对象的告警、发生条件和相关记录。

图表有了数字，还需要有解释

图表形式适合回答的问题交付前需要补齐
指标卡当前状态是否值得进一步查看指标定义、单位、统计窗口、更新时间与比较基准
时间趋势变化发生在什么时候时间粒度、缺失数据表示和发布等事件的关联线索
分布与排行哪些类型或对象更突出类别含义、分母、排序依据，以及进入明细的方式

对于耗时分布，均值和长尾回答的问题不同。保留区间分布有助于避免只看平均数；如果下一轮加入分位数，也需要明确采样方式，而不能为了让图表显得专业就再堆一排数字。

处理动作，应留下可继续接手的状态

追踪、处理、转让、关闭和删除承担不同职责：有的用于观察，有的用于分配，有的会改变事件状态。界面需要说明何时可用、影响什么，以及结果在哪里查看；角色权限与状态流转在交付时与业务共同确认。

  1. 确认对象核对环境、模块、等级和事件标识，再进入处理。
  2. 补足上下文从详情获得发生条件和相关证据，记录仍待确认的信息。
  3. 执行与交接处理或转让后留下责任人、时间与结论，关闭前确认依据，便于后来者接手。

配置页，把规则写成可理解的行为

规则类型规则对应的行为应避免的理解混淆
时间过滤在指定时间窗口内不重复发送告警抑制重复通知不等于事件消失，应保留被过滤记录的查询线索
高危追踪指定时长后仍未关闭则继续推送追踪周期不等于故障持续时长；停止条件和接收对象需明确
累计过滤累计到指定次数后触发正式告警计数范围、时间窗口和重置条件需说明，不能只显示一个阈值

内部工具的完成度，体现在交付细节

我希望这套后台帮助团队逐步收窄问题：入口确定范围，列表定位对象，详情解释事件，看板提供观察尺度，配置说明系统行为。统一组件之外，命名、状态语义与处理结果也需要保持一致。

  • 组件规则列表、筛选、状态标签、图表标题、信息组和就地表单保持一致，区分空值、加载中与请求失败。
  • 交互走查覆盖筛选后进入详情再返回、长标识查看、跨环境切换、批量操作和保存失败。
  • 协作交付与开发确认指标口径、状态转换及字段约束，将正常、异常与恢复路径写入组件说明。

下一轮会用具体事件的追查任务与配置回放检验设计，观察定位错误、上下文丢失和交接中断发生在哪里。监控覆盖、恢复时间与告警数量还受技术策略影响，需要与交互体验分开评价。
